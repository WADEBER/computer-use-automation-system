## 3. Findings

### 3.1 [SEC-001] Validation errors echo the offending config value to stderr — **Low**

- **File:** [src/computer_use_automation_system/cli.py:171](src/computer_use_automation_system/cli.py#L171) (message built from `exc` raised at [src/computer_use_automation_system/replay/taxonomy.py:90](src/computer_use_automation_system/replay/taxonomy.py#L90))
- **CWE:** CWE-209 (Generation of Error Message Containing Sensitive Information)
- **OWASP:** A09 — Security Logging and Monitoring Failures (error-output hygiene; approximate mapping)
- **Confidence:** Confirmed (reproduced: `str(ValidationError)` contains `input_value=['SENSITIVE-PII-VALUE', '']`)
- **Tool:** manual review + reproduction script

**Description**

When `config/taxonomy.json` fails validation, the CLI prints `str(exc)` to stderr. Pydantic v2 includes the raw `input_value` of the offending field in the error string, so whatever content sits in that field is echoed verbatim to the terminal and to any log capturing stderr.

**Vulnerable code**

```python
# src/computer_use_automation_system/cli.py:171
try:
    load_taxonomy()  # eager validation: bad config -> exit 2, no hot crash
except (OSError, ValidationError) as exc:
    print(f"replay: invalid taxonomy config: {exc}", file=sys.stderr)
    return 2
```

**Impact**

Local information disclosure: a sensitive string present in a misconfigured field (e.g. a pattern copied from production UI text containing PII) is printed to stderr. Attacker control is nil (local operator-owned config), and the exposure surface is the operator's own terminal/log — hence Low.

**Reproduction / PoC sketch** (do NOT run)

> Put a sensitive string into a `patterns` list together with an empty entry, run `replay`; stderr shows `input_value=['SENSITIVE-PII-VALUE', '']`.

**Remediation**

```python
# src/computer_use_automation_system/cli.py:171 — fixed
except (OSError, ValidationError) as exc:
    if isinstance(exc, ValidationError):
        locs = ", ".join(".".join(str(p) for p in e["loc"]) for e in exc.errors())
        print(f"replay: invalid taxonomy config at: {locs}", file=sys.stderr)
    else:
        print("replay: taxonomy config unreadable", file=sys.stderr)
    return 2
```

Report locations only (which field failed), never the raw input values. File-not-found may keep the path (it is operator-supplied), but drop `str(exc)` for validation errors.

**References**
- [CWE-209](https://cwe.mitre.org/data/definitions/209.html)
- [Pydantic v2 errors API](https://docs.pydantic.dev/latest/concepts/validation_errors/)

### 3.2 [SEC-002] CRLF in taxonomy patterns forges CLI output lines — **Low**

- **File:** [src/computer_use_automation_system/replay/taxonomy.py:142](src/computer_use_automation_system/replay/taxonomy.py#L142) (pattern interpolated into signal; passes through [src/computer_use_automation_system/replay/engine.py:263](src/computer_use_automation_system/replay/engine.py#L263) and printed at [src/computer_use_automation_system/cli.py:161](src/computer_use_automation_system/cli.py#L161))
- **CWE:** CWE-117 (Improper Output Neutralization for Logs)
- **OWASP:** A09 — Security Logging and Monitoring Failures
- **Confidence:** Confirmed (reproduced: `redact_text` returns the string with `chr(10)` intact)
- **Tool:** manual review + reproduction script

**Description**

`Classification.signal` embeds the matched config pattern verbatim (`f"page pattern: {pattern}"`). The engine embeds `signal` into `error.message` and only applies `redact_text`, which masks secrets but does not strip CR/LF. The CLI prints the message with `print()`, so a pattern containing a newline splits the result line and lets an attacker-controlled (config-writing) party append forged content that looks like engine output.

**Vulnerable code**

```python
# src/computer_use_automation_system/replay/taxonomy.py:142
return Classification("business_outcome", f"page pattern: {pattern}")
...
# src/computer_use_automation_system/cli.py:161
print(f"replay failure: stage={error.stage.value}{step}{kind}{category} {error.message}")
```

**Impact**

Output/log forgery: a crafted `taxonomy.json` pattern like `"x\nreplay success: ..."` makes the CLI emit a second line that mimics a legitimate result, potentially misleading a human operator or a log parser. Requires write access to the config file (operator or compromised repo), so severity is Low.

**Reproduction / PoC sketch** (do NOT run)

> Set a `business_outcome` pattern containing `\n` + a fake success line; trigger a failure matching it; observe two lines printed for one result, the second looking like genuine engine output.

**Remediation**

```python
# src/computer_use_automation_system/replay/taxonomy.py:29 — fixed
def _non_empty_strings(values: list[str]) -> list[str]:
    for value in values:
        if not value.strip():
            raise ValueError("patterns must not contain empty strings")
        if any(ord(ch) < 32 for ch in value):
            raise ValueError("patterns must not contain control characters")
    return values
```

Defense in depth: additionally neutralize control characters in the CLI line (`error.message.replace("\n", " ").replace("\r", " ")`) so the print layer is safe regardless of the source.

**References**
- [CWE-117](https://cwe.mitre.org/data/definitions/117.html)
- [OWASP Log Injection Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Log_Injection_Prevention_Cheat_Sheet.html)

### 3.3 [SEC-003] Time budget not re-checked during bounded retries — **Info**

- **File:** [src/computer_use_automation_system/replay/engine.py:196](src/computer_use_automation_system/replay/engine.py#L196) (checked once per step) vs [src/computer_use_automation_system/replay/engine.py:209](src/computer_use_automation_system/replay/engine.py#L209) (retry loop)
- **CWE:** CWE-400 (Uncontrolled Resource Consumption)
- **OWASP:** A05 — Security Misconfiguration (approximate mapping for budget handling)
- **Confidence:** Confirmed (code read)
- **Tool:** manual review

**Description**

The `step_timeout_ms` budget is evaluated once, before a step's retry loop. Recoverable retries inside the same step do not re-check it, so actual elapsed time can exceed `--max-timeout-ms` by up to `(attempts - 1) x driver-step-time`.

**Impact**

Bounded overshoot of the operator's time budget on a local CLI. Loop is strictly bounded (`max_recoverable_attempts >= 1` validated, no `time.sleep`), so there is no unbounded consumption or hang. No exploitation path beyond a slightly longer run.

**Remediation**

```python
# src/computer_use_automation_system/replay/engine.py:209 — fixed
while True:
    attempts += 1
    if step_timeout_ms is not None:
        spent_ms = int((clock() - started) * 1000)
        if spent_ms > step_timeout_ms:
            return _failure(ReplayStage.STEP, "replay time budget exceeded", ...)
    ...
```

**References**
- [CWE-400](https://cwe.mitre.org/data/definitions/400.html)
