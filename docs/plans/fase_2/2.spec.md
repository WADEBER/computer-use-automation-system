## Problema y objetivo

**Problema**: El sistema no tiene target real sobre el que automatizar. El placeholder Flask de la Fase 1 no ofrece ningún flujo; sin una UI bancaria multi-step local, las fases 5-8 (discovery, replay, taxonomía de errores, HITL) no tendrían dónde ejecutarse y la evidencia del take-home sería imposible de producir.

**Objetivo**: Una app Flask local dentro del repo que simula un back-office bancario legado con un flujo real **member search -> member detail -> loan disbursement con confirmación**, datos seed deterministas en memoria, escenarios de excepción (no found, validación) y superficie de marcado intencionadamente realista — verificable con tests de humo y ejecutable a mano con un comando documentado.

## Historias de usuario

### HU-1: Ejecutar el target localmente
**Como** desarrollador (o agente) del proyecto,
**quiero** levantar la proxy app con un único comando documentado,
**para** recorrer el flujo a mano en el navegador antes de automatizarlo.

**Criterios de aceptación:**
- [x] `uv run python -m proxy_app.app` sirve en `http://127.0.0.1:5000` (host/puerto configurables por `PROXY_APP_HOST`/`PROXY_APP_PORT`)
- [x] El comando está documentado en `README.md` (sección de comandos)
- [x] A mano se puede completar: buscar un miembro -> ver detalle -> desembolsar préstamo -> ver recibo

### HU-2: Superficie multi-step automatizable
**Como** motor de discovery/replay (Fases 5-6),
**quiero** un flujo de 3+ pasos con formularios, navegación y acción final,
**para** que el LLM tenga decisiones reales que descubrir y el replay tenga pasos que reejecutar.

**Criterios de aceptación:**
- [x] Flujo core: search (GET con query) -> results/detail (GET) -> formulario de desembolso (POST) -> confirmación -> recibo
- [x] La búsqueda soporta al menos: resultado encontrado, y consulta sin resultados ("member not found" como business outcome, HTTP 200 con mensaje, no crash)
- [x] El marcado es de estilo legado/realista: sin `data-testid`, selectores imperfectos (names, tablas, ids heredados aceptables)
- [x] Acceso al detalle y al formulario funciona solo con el ID del miembro (sin estado oculto irrecuperable)

### HU-3: Excepciones y validación
**Como** tester de la taxonomía de errores (Fase 7),
**quiero** escenarios de excepción embebidos en la UI,
**para** que el sistema demuestre business outcome vs hard failure sobre superficie real.

**Criterios de aceptación:**
- [x] "Member not found": búsqueda sin resultados muestra mensaje de negocio en la página (no excepción, no 500)
- [x] Validación de desembolso: monto vacío, no numérico o <= 0 devuelve el formulario con errores de validación visibles (estado de validación)
- [x] Modal/paso de confirmación antes de ejecutar el desembolso (la acción no ocurre con el primer POST)
- [x] El desembolso exitoso muestra un recibo con datos concretos (miembro, monto, número de operación)

## Contratos de datos

### Entidades (en memoria, seed determinista)

**Member**

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| member_id | str | PK, formato `M-1001` style, único |
| full_name | str | display en detalle y recibo |
| accounts | list[Account] | >= 1 cuenta |
| credit_limit | Decimal/float | techo del desembolso |

**Account**

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| account_id | str | PK, único por miembro |
| type | str | p.ej. `checking`, `savings` |
| balance | Decimal/float | >= 0, determinista |

**Loan disbursement (transacción, no persistida entre reinicios)**

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| member_id | str | debe existir en seed |
| account_id | str | debe pertenecer al miembro |
| amount | float | requerida, numérica, > 0, <= credit_limit |
| disbursement_no | str | generado deterministamente (p.ej. `DISB-0001` correlativo en sesión) |

**Invariantes:**
- El seed es idéntico en cada arranque: mismos IDs, nombres y saldos.
- Un desembolso nunca deja la cuenta en saldo negativo más allá del permitido por `credit_limit` (validación en servidor).
- Los datos seed viven en memoria a nivel de app (se resetean al reiniciar); sin BD ni archivos.

### Endpoints (Flask, HTML server-rendered)

**GET /** — Landing con formulario de búsqueda de miembros.
- Response 200: HTML con `<form>` de búsqueda (`q` o similar).

**GET /members/search?q=<texto>**
- 200 + lista de resultados (tabla con member_id, nombre) si hay matches.
- 200 + mensaje "member not found" si no hay matches (business outcome, nunca 4xx/5xx).

**GET /members/<member_id>** — Detalle del miembro.
- 200: nombre, cuentas con saldo, crédito disponible, enlace/formulario al desembolso.
- 404 con página de error amigable si el ID no existe (IDs inventados -> hard failure legítimo para tests).

**POST /members/<member_id>/loans/disburse** — Valida el desembolso.
- Request form: `account_id`, `amount`.
- Si validación falla → 200 re-render del formulario con mensajes de error (no redirect, no 4xx).
- Si validación OK → 200 con resumen + paso de confirmación (modal o página intermedia); **no ejecuta aún**.

**POST /members/<member_id>/loans/disburse/execute** — Ejecuta lo confirmado.
- Request form: mismos campos (+hidden del paso anterior si aplica).
- 200: página de recibo con `disbursement_no`, miembro, cuenta, monto y saldo resultante.
- Si el resumen no es válido/expirado → 200 con mensaje de error controlado (no 500).

## Restricciones

- **Flask** (decisión de usuario en scaffold), Python 3.11, sin Docker.
- **In-memory**: sin SQLite/ORM/archivos de datos; seed en módulo Python.
- **Inglés**: toda la UI, mensajes y HTML en inglés (entregable del take-home).
- **Marcado realista**: sin `data-testid`; se acepta marcado heredado (tablas, atributos legacy, nombres repetidos). La automatización no debe depender de IDs perfectos.
- **Determinismo**: mismo seed en cada arranque; generación de `disbursement_no` predecible por sesión.
- **Config por env**: reutilizar `resolve_config()` existente (`PROXY_APP_HOST/PORT`); no romper el comportamiento debug-off de seguridad (B201 de Fase 1).
- **Sin `time.sleep` ni dependencia de timing** en tests (usar `test_client` síncrono).
- **Tests en verde**: `uv run pytest`, `ruff`, `bandit` pasan al cierre.

---

## Anti-objetivos (lo que esta fase NO hace)

- NO implementa el motor de automatización (discovery/replay) — solo es el target.
- NO incluye autenticación, HTTPS, rate limiting ni hardening de producción.
- NO persiste datos entre reinicios (in-memory por decisión).
- NO añade Docker, colas ni infraestructura.
- NO expone API JSON/REST — es HTML server-rendered (un back-office legado).
- NO usa frameworks CSS modernos ni frontend build step (HTML plano, CSS inline/estático mínimo).
- NO ofrece test IDs perfectos ni accessibility tree pulido — la realismo es intencional.
- NO implementa los escenarios completos de Fase 7 (session timeout, permission denial, load failure) — aquí solo: not found, validación, confirmación.
