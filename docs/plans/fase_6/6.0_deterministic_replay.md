# Fase 6: Deterministic Replay Engine

> Spec funcional: `docs/plans/fase_6/6.spec.md`
> Este plan implementa los requisitos definidos en la spec anterior.

## Objetivo

Una función tipada `replay(artifact, inputs, driver, policy)` y el subcomando `replay` de la CLI que ejecutan el artefacto **paso a paso y de forma determinista** — sin ninguna llamada al LLM — validando inputs contra `input_schema`, resolviendo `{{input.*}}`, localizando con cadena de fallback bajo `WebDriverWait`, pasando cada acción por `enforce()` de Fase 4, verificando el `checkpoint` antes de declarar éxito y devolviendo un `ReplayResult` tipado con `outputs` conformes a `output_schema`. CI con fakes (sin Chrome ni Ollama).

## Notas / Decisiones técnicas

1. **Reutilización desde discovery (sin refactor)**: el engine importa `discovery.act.perform` y `discovery.selenium_driver.locator_to_by`. La spec prohíbe importar solo `decide`/`goal`/`llm_client`/`ollama` (el test estático lo verifica); mover código a un módulo compartido tocaría una fase cerrada y se deja para una eventual desviación `6.1`.
2. **Validación de schemas sin codegen**: `input_schema`/`output_schema` son `JSONSchemaObject` (properties + required + type por propiedad). Se valida con un validador de diccionario (required presente, type en `str/int/float/bool`) en vez de `pydantic.create_model` dinámico — mismo resultado, cero magia, errores con `stage` propio.
3. **URL para `enforce`** (misma regla que Fase 5, nota 3): `navigate` evalúa la URL **objetivo** (`value` resuelto); el resto de acciones evalúan `current_url` del driver.
4. **Semántica de `expected_condition`** (Fase 3 solo define el enum):
   - `visible` -> cualquier locator del checkpoint resuelve y el elemento está visible;
   - `text_present` -> el elemento resuelto tiene texto no vacío;
   - `url_contains` -> la URL actual contiene el valor esperado, tomado del primer locator del checkpoint cuyo `value` sea `http(s)://`; si no existe tal locator, la condición **falla** (fail-closed) con mensaje claro. La fixture feliz usa `text_present`.
   Ambos primeros casos usan fallback de locators + `WebDriverWait`; localizador agotado = checkpoint fallido (no excepción).
5. **Exit codes**: `0` success; `10` blocked; `11` needs_approval; `1` cualquier otra failure; `2` usage de argparse/artefacto inválido (espejo de `discover`, sin colisión).
6. **Determinismo**: `clock: Callable[[], float] = time.monotonic` inyectable para `elapsed_ms` (patrón del runner de Fase 5); misma entrada -> misma secuencia y mismos outputs, testeado con `FakeDriver`.
7. **Sin LLM**: `replay/` no importa nada de `decide`/`goal`/`llm_client`/`ollama`; el test estático barre los imports del paquete (regresión contra futuras "ayudas" del modelo).
8. **`decisions` siempre presente**: la traza de políticas se registra tanto en success como en failure (para debug y para Fase 7); `outputs` solo en success (invariante de la spec).
9. **`type` step**: `clear()` + `send_keys(valor)` (semántica de Fase 5); el valor resuelto **no** se registra en `ReplayResult` (evita PII en el resultado — la spec exige `message` sin datos sensibles; si hiciera falta preview, pasaría por `redact_text`).
10. **CLI**: patrón idéntico a `discover` — `_execute(...)` monkeypatcheable para tests, `load_dotenv()` solo en CLI, parsing estricto cuando `replay` está en args.
11. **CI**: ningún test instancia Selenium/Chrome; el `FakeDriver` existente de Fase 5 navega por `href` con `urljoin` y ya soporta `click`/`type`/`navigate`/`extract` sobre una superficie simulada de la fixture (extender solo si `select` u otra semántica lo requiere).
12. **Desviación menor (CA HU-2 fallback)**: cada locator se resuelve con su propio `WebDriverWait` (patrón de Fase 5, `selenium_driver._find`) y sin `time.sleep()`, pero el tiempo de espera es el `timeout_s` del driver (10s por defecto, `build_webdriver(timeout_s=...)`) — el campo `step.timeout_ms` del artefacto **no se propaga** al WebDriverWait (requeriría tocar el protocolo `BrowserDriver` de Fase 5, fase cerrada). El presupuesto de tiempo global sí existe vía `--max-timeout-ms` (chequeo entre steps con el `clock` inyectable). Si se quiere el timeout estricto por step, plantearlo como desviación `6.1`.
