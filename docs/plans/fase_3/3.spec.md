# Spec Fase 3: Artifact Schema

> Especificación funcional — QUÉ construir y POR QUÉ.
> El CÓMO se define en el plan de fase (3.0_artifact_schema.md).
> Los criterios de aceptación se verifican con `/7-verificar` al terminar la fase.

---

## Problema y objetivo

**Problema**: Sin un contrato tipado de artefacto, el discovery loop (Fase 5) no tiene cómo serializar lo aprendido y el replay determinista (Fase 6) no tiene qué consumir. El Assignment §3.2 declara el schema como "focal point of the evaluation": un reviewer humano y un agente invocador deben entender la capacidad (qué hace, qué necesita, qué devuelve) solo leyendo el artefacto.

**Objetivo**: Modelos Pydantic tipados + archivo `artifact.schema.json` exportado, con validación estricta, fixtures válida/inválida y tests round-trip: la fixture válida pasa, las inválidas fallan con error claro que nombra el campo, y el schema está documentado en inglés.

## Historias de usuario

### HU-1: El artefacto se entiende sin contexto adicional
**Como** reviewer humano (o agente invocador),
**quiero** metadatos completos y versionados en el artefacto,
**para** saber qué capacidad es, para qué app sirve y qué versión corre antes de ejecutar nada.

**Criterios de aceptación:**
- [x] `capability_id` (snake_case), `version` (semver `X.Y.Z`), `description` (no vacía, inglés) y `target_app` (`name` + `entry_url`) son obligatorios
- [x] Un artefacto sin cualquiera de estos campos falla validación con error que nombra el campo faltante

### HU-2: El discovery puede serializar un flujo con fallback de localización
**Como** bucle de discovery (Fase 5),
**quiero** steps ordenados con array priorizado de locators y acciones tipadas,
**para** grabar el flujo de forma robusta frente a variaciones de la UI.

**Criterios de aceptación:**
- [x] `steps` no vacío, `step_id` secuencial (1..n), orden preservado al serializar
- [x] `action_type` ∈ {`navigate`, `click`, `type`, `extract`, `select`}
- [x] Cada step y el checkpoint llevan `locators` (>= 1) como array **priorizado** — el orden del array es el orden de fallback
- [x] `locator.type` ∈ {`id`, `css`, `xpath`, `role`, `text`} (cobertura id → css → xpath semántico / role / text)
- [x] Steps `type`/`select` exigen `value` con al menos una referencia `{{input.*}}` (sin valores de corrida hardcodeados)
- [x] Todo `{{input.X}}` referenciado existe en `input_schema.properties` (referencia huérfana = error de validación)
- [x] `timeout_ms` opcional (> 0, default 5000)

### HU-3: El replay recibe contratos tipados y checkpoint verificable
**Como** motor de replay (Fase 6),
**quiero** `input_schema`, `output_schema` y `checkpoint` estrictos,
**para** invocar la capacidad con parámetros tipados y verificar el éxito antes de declarar resultado.

**Criterios de aceptación:**
- [x] `input_schema`/`output_schema`: objeto JSON-Schema-like (`type: "object"`, `properties` con `type` por campo, `required` subconjunto de `properties`)
- [x] `checkpoint` obligatorio: `description`, `locators` (>= 1), `expected_condition` ∈ {`visible`, `text_present`, `url_contains`}
- [x] Steps `extract` exigen `output_key` presente en `output_schema.properties`
- [x] Un artefacto sin checkpoint o con condición desconocida falla validación con error claro

### HU-4: Validación estricta, fixtures y round-trip
**Como** desarrollador del sistema,
**quiero** fixtures de ejemplo y tests de round-trip,
**para** garantizar que load/save/validate son correctos y el schema no deriva silenciosamente.

**Criterios de aceptación:**
- [x] Fixture válida (`tests/fixtures/valid_artifact.json`) pasa validación
- [x] >= 3 fixtures inválidas fallan validación, cada una con error que identifica el campo/regla (al menos: locator type inválido, referencia `{{input.*}}` huérfana, checkpoint ausente)
- [x] Round-trip: JSON -> modelo -> JSON preserva el contenido (test de ida y vuelta)
- [x] `artifact.schema.json` exportado existe y coincide con `Artifact.model_json_schema()` (test anti-deriva)
- [x] Documentación del schema en inglés (docstrings de modelos + archivo exportado)

## Contratos de datos

### Artefacto (raíz)

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| capability_id | str | obligatorio, `^[a-z][a-z0-9_]*$` (snake_case) |
| version | str | obligatorio, semver `^\d+\.\d+\.\d+$` |
| description | str | obligatoria, no vacía |
| target_app | TargetApp | `{ name: str, entry_url: str (http/https) }` |
| input_schema | JSONSchemaObject | `type="object"`, `properties` no vacío, `required` ⊆ keys de properties |
| output_schema | JSONSchemaObject | ídem |
| steps | list[Step] | >= 1; `step_id` secuencial 1..n; orden estable |
| checkpoint | Checkpoint | obligatorio |

### Step

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| step_id | int | >= 1, secuencial por posición |
| action_type | enum | `navigate` \| `click` \| `type` \| `extract` \| `select` |
| description | str | no vacía (inglés) |
| locators | list[Locator] | >= 1, orden = prioridad de fallback |
| value | str \| ausente | requerido para `type`/`select` con `{{input.*}}`; para `navigate` = URL destino; prohibido en `click`/`extract` |
| output_key | str \| ausente | requerido para `extract` y debe ∈ `output_schema.properties`; prohibido en el resto |
| timeout_ms | int | opcional, > 0, default 5000 |

### Locator

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| type | enum | `id` \| `css` \| `xpath` \| `role` \| `text` |
| value | str | no vacío |

### Checkpoint

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| description | str | no vacía |
| locators | list[Locator] | >= 1 |
| expected_condition | enum | `visible` \| `text_present` \| `url_contains` |

### JSONSchemaObject (input/output)

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| type | str | fijo `"object"` |
| properties | dict[str, object] | no vacío; cada campo con al menos `type: str` |
| required | list[str] | opcional; cada elemento ∈ keys de `properties` |

**Invariantes (validación cruzada):**
- Todo `{{input.X}}` en cualquier `value` → `X` ∈ `input_schema.properties`.
- Todo `output_key` de steps `extract` → ∈ `output_schema.properties`.
- `step_id` de la posición i == i+1.
- El orden de `locators` se preserva en round-trip (es semántico: prioridad).

### Archivos de esquema

| Archivo | Qué contiene |
|---------|--------------|
| `tests/fixtures/valid_artifact.json` | Artefacto de ejemplo completo y válido (flujo realista tipo `lookup_member_balance` contra la proxy app) |
| `tests/fixtures/invalid/*.json` | >= 3 inválidos, uno por regla clave |
| `docs/schemas/artifact.schema.json` | JSON Schema exportado desde Pydantic (`model_json_schema()`), en inglés — contrato reviewable |

## Restricciones

- **Pydantic 2.13** (ya en deps) — **sin dependencias nuevas** (no `jsonschema`; Pydantic genera el JSON Schema con `model_json_schema()`).
- **Python 3.11**, uv, ruff (línea 100), mypy opcional — suite en verde al cierre.
- **Inglés** en modelos (docstrings), fixtures y schema exportado.
- **Serialización JSON** estable: load/save idempotente, sin claves extra silenciosas (`extra="forbid"`).
- **Sin Unicode especial** en strings Python (convención CLAUDE.md).

---

## Anti-objetivos (lo que esta fase NO hace)

- NO implementa el discovery loop ni el replay (solo el contrato que consumirán — Fases 5/6).
- NO valida los **valores de runtime** contra `input_schema` (eso es responsabilidad del replay al invocar).
- NO almacena artefactos en disco en rutas de ejecución ni expone CLI/catalog (Fase 5/9; aquí solo fixtures).
- NO añade dependencias nuevas a `pyproject.toml`.
- NO incluye campos multi-tenant/tenant_id/drift (diseño de REPORT §4, no implementación).
- NO resuelve redacción de PII/secretos dentro del artefacto (Fase 4).
