# Spec Fase 4: Safety & Policy Core

> Especificación funcional — QUÉ construir y POR QUÉ.
> El CÓMO se define en el plan de fase (4.0_safety_policy_core.md).
> Los criterios de aceptación se verifican con `/7-verificar` al terminar la fase.

---

## Problema y objetivo

**Problema**: el sistema dará "manos" a un agente sobre una aplicación bancaria con datos regulados, pero todavía no existe ningún guardrail entre la decisión del agente y la acción: nada impide navegar fuera del dominio permitido, nada obliga a una aprobación humana antes de una operación irreversible (un desembolso), y nada impide que secretos o PII financiera (nombres, cuentas, saldos) acaben crudos en los logs o en la evidencia que se entregará. Sin esto, el discovery y el replay de las Fases 5/6 serían inseguros por construcción.

**Objetivo**: un núcleo de política ejecutable —allowlist configurable en JSON validado con Pydantic y clasificación de acciones con cuatro veredictos (`allow` / `confirm` / `flag` / `block`)— más una capa de redacción aplicada en el punto de escritura (logging y ficheros de evidencia). El éxito se ve cuando los tests negativos demuestran que nada fuera de la política pasa, que lo irreversible exige aprobación explícita, y que ningún log ni fichero escrito contiene secretos ni PII en claro.

## Historias de usuario

### HU-1: El perímetro de seguridad es configurable sin tocar código
**Como** operador/maintainer del sistema,
**quiero** la allowlist (URLs, rutas y tipos de acción) en un fichero JSON versionado y validado con Pydantic,
**para** poder cambiar el perímetro con una revisión de código, sin modificar el motor.

**Criterios de aceptación:**
- [x] `config/policy.json` existe, está versionado, es reviewable y no contiene secretos reales (solo patrones/literales de redacción).
- [x] El fichero se valida con Pydantic (`extra="forbid"`): un campo obligatorio ausente, un extra o un tipo inválido hacen fallar la carga con un error que **nombra el campo**.
- [x] El perímetro declara (los tres mínimos): orígenes/URLs permitidos (>= 1), rutas permitidas (>= 1) y tipos de acción permitidos (>= 1, subconjunto de los `ActionType` de Fase 3).
- [x] Cambiar la allowlist produce veredictos distintos sin cambiar ni una línea de código (test con dos políticas distintas).

### HU-2: Nada actúa fuera de la allowlist (enforcement con tests negativos)
**Como** operador del sistema,
**quiero** una única función de evaluación que reciba una acción (tipo + URL) y devuelva un veredicto justificado,
**para** que discovery y replay compartan el mismo guardrail duro, determinista y sin LLM.

**Criterios de aceptación:**
- [x] API única de evaluación `(policy, action_type, url) -> Decision` (veredicto + `reason`), consumible por Fases 5/6.
- [x] Test negativo: URL fuera de los orígenes permitidos (p. ej. un dominio externo) -> `block`.
- [x] Test negativo: ruta fuera de las rutas permitidas -> `block`.
- [x] Test negativo: tipo de acción no incluido en la allowlist -> `block`.
- [x] `enforce` (envoltorio de la evaluación) lanza un error tipado ante `block` — la acción jamás "pasa en silencio".
- [x] Dentro del perímetro, la evaluación devuelve un veredicto distinto de `block`.

### HU-3: Las acciones se clasifican con veredictos justificados
**Como** reviewer humano del sistema,
**quiero** que cada acción reciba un veredicto con su razón escrita en la propia política,
**para** poder auditar por qué algo se bloquea, exige confirmación o solo se marca.

**Criterios de aceptación:**
- [x] `allow` para acciones seguras/reversibles: `navigate`, `click` de navegación, `type`/`select` (escribir es reversible; lo irreversible queda gateado abajo) — dentro del perímetro.
- [x] `confirm` para la ejecución financiera: regla que matchea rutas `*/execute` (p. ej. Confirm Disbursement) -> `enforce` **rechaza** si no hay aprobación explícita, y la aprueba si la hay (test de ambos caminos).
- [x] `flag` para lecturas de dato sensible: regla `extract` -> veredicto permitido pero marcado en `Decision` para la traza de auditoría.
- [x] `block` para todo lo fuera de la allowlist (ver HU-2).
- [x] Cada regla de la política lleva un `reason` no vacío; las reglas se evalúan en orden y **gana la primera que coincide** (test de orden).
- [x] Hay al menos un test por cada uno de los cuatro veredictos.

### HU-4: Los secretos y la PII no llegan crudos a la escritura
**Como** responsable de seguridad/auditoría,
**quiero** redacción en la capa de escritura (no "acordarse" de redactar en cada llamada),
**para** que ningún log ni fichero de evidencia contenga PII financiera ni secretos en claro.

**Criterios de aceptación:**
- [x] Redacción de texto libre: secretos (p. ej. `KEY=value`, tokens `sk-...`), números de cuenta (`CHK-2201`), importes con decimales (`4250.75`) y literales de la lista (nombres del seed) se sustituyen por máscaras (`[REDACTED_SECRET]`, `CHK-****01`, `[REDACTED_AMOUNT]`, `[REDACTED_NAME]`).
- [x] Redacción estructurada: un dict/JSON de log o artefacto sale con los valores de las claves sensibles (`full_name`, `balance`, `amount`, `credit_limit`, `account_id`...) enmascarados.
- [x] Filtro de logging: el mensaje que llega al handler ya está redactado (test con handler en memoria que adjunta el filtro al logger).
- [x] Capa de escritura de ficheros: todo texto escrito a disco pasa por la redacción (test: el contenido del fichero en disco no contiene PII ni secretos de prueba).
- [x] Se conservan sin tocar: `member_id` (`M-1001`), URLs, `step_id` y tipos de acción (test: aparecen intactos tras la redacción).
- [x] Redacción idempotente: aplicarla dos veces produce el mismo resultado.
- [x] Patrones, literales y claves a redactar viven en `config/policy.json` (mismo fichero que la allowlist), no hardcodeados en el motor.

## Contratos de datos

### `config/policy.json` (raíz de la política)

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| allowed_origins | list[str] | >= 1; prefijos de URL exactos (p. ej. `http://127.0.0.1:5000/`) |
| allowed_routes | list[str] | >= 1; prefijos de ruta (p. ej. `/members`) |
| allowed_action_types | list[ActionType] | >= 1; subconjunto de los `ActionType` de Fase 3 (`navigate`, `click`, `type`, `extract`, `select`) |
| rules | list[PolicyRule] | >= 0; orden de evaluación, primera coincidencia gana |
| redaction | RedactionConfig | obligatorio |

### `PolicyRule`

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| match_action_type | ActionType | opcional |
| match_url_pattern | str | opcional; patrón sobre la ruta (p. ej. `*/execute`) |
| decision | enum | `allow` \| `confirm` \| `flag` \| `block` |
| reason | str | obligatorio, no vacío (justificación auditable) |

**Invariantes:**
- Toda regla debe declarar al menos una condición de match (`match_action_type` o `match_url_pattern`).
- Orden = prioridad: la primera regla que coincide decide; si ninguna coincide y la acción está en el perímetro -> `allow`.

### `RedactionConfig`

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| patterns | list[{name, regex, replacement}] | >= 1; `regex` válida; `replacement` la máscara |
| literals | list[str] | >= 1 (p. ej. nombres del seed) |
| field_keys | list[str] | >= 1; claves sensibles de dicts estructurados |

### `Decision` (salida de la evaluación)

| Campo | Tipo | Restricciones |
|-------|------|---------------|
| decision | enum | `allow` \| `confirm` \| `flag` \| `block` |
| reason | str | siempre presente (de la regla o del perímetro) |
| matched_rule | str \| ausente | razón/id de la regla que decidió, si hubo match |

**Invariantes (validación cruzada):**
- Perímetro primero, reglas después, `allow` por defecto: `block` por perímetro no se puede "neutralizar" con una regla posterior.
- `confirm` sin aprobación explícita -> la capa `enforce` rechaza con error tipado.
- La redacción comparte UNA sola `RedactionConfig`: el filtro de logging y el writer de ficheros usan exactamente la misma (fuente única).
- Idempotencia: `redact(redact(x)) == redact(x)`.

### Ejemplo mínimo de `config/policy.json`

```json
{
  "allowed_origins": ["http://127.0.0.1:5000/"],
  "allowed_routes": ["/", "/members"],
  "allowed_action_types": ["navigate", "click", "type", "extract", "select"],
  "rules": [
    {"match_url_pattern": "*/execute", "decision": "confirm", "reason": "Irreversible financial execution requires human approval"},
    {"match_action_type": "extract", "decision": "flag", "reason": "Read of regulated personal/financial data leaves an audit mark"}
  ],
  "redaction": {
    "patterns": [
      {"name": "secret_assignment", "regex": "(?i)(api[_-]?key|token|secret|password)\\s*[=:]\\s*\\S+", "replacement": "[REDACTED_SECRET]"},
      {"name": "account_number", "regex": "\\b([A-Z]{3}-)\\d{2}(\\d{2})\\b", "replacement": "\\1****\\2"},
      {"name": "money_amount", "regex": "\\b\\d+\\.\\d{2}\\b", "replacement": "[REDACTED_AMOUNT]"}
    ],
    "literals": ["Alice Hartwell", "Brian Okafor", "Carla Mendes"],
    "field_keys": ["full_name", "member_name", "account_id", "balance", "amount", "credit_limit", "new_balance"]
  }
}
```

## Restricciones

- **Sin dependencias nuevas**: Pydantic 2.13 (ya en deps) + librería estándar `re`.
- **Python 3.11**, ruff (línea 100, target `py311`), mypy opcional — suite completa en verde al cierre.
- **Inglés** en código y docstrings; sin Unicode especial en `print()`/logging de Python (convención CLAUDE.md).
- **`config/policy.json` versionado sin credenciales reales**: solo patrones y literales de ejemplo.
- **`/8-auditar` obligatorio** al cerrar esta fase (toca seguridad): informe en `docs/security/` sin hallazgos Critical/High abiertos.

## Anti-objetivos (lo que esta fase NO hace)

- NO implementa discovery, replay ni HITL (Fases 5/6/8) — solo la API de política y redacción que consumirán.
- NO hace enforcement a nivel de red, proxy del sistema operativo ni sandbox: es guardrail **en proceso**, invocado por el motor.
- NO modifica ni intercepta la proxy app (`src/proxy_app/` queda intacta).
- NO incluye UI ni editor de política: el fichero JSON versionado *es* la configuración.
- NO implementa compliance framework (GDPR/PCI-DSS), cifrado en reposo, vault de secretos ni DLP externo.
- NO resuelve la redacción de datos **dentro** de la UI mostrada al LLM (observe/decide llega en Fase 5).
- NO añade dependencias nuevas a `pyproject.toml`.
